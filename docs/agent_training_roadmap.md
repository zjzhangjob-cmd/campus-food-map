# 小觅 Agent 训练复盘与下一阶段路线

## 1. 本次问题复盘

用户问“社群相关事项”却触发兜底餐厅，根因不是模型参数，而是意图门控设计不完整：

1. 产品意图识别太窄  
   之前只有“是什么/怎么用/入口在哪”等问法才会进入产品功能回答。用户说“社群相关事项”“社区有什么内容”这类自然表达时，会漏到推荐逻辑。

2. 兜底机制单一  
   原兜底更偏“回到餐厅推荐”，没有先区分用户是在问产品功能、泛问题、地图重排，还是餐饮需求。

3. 评测集覆盖不够贴近真实说法  
   评测里有“社区圈是什么”，但缺少“社群相关事项”“这个产品还能干嘛”“我随便问个问题你会做什么”等非标准问法。

4. 产品词有双重含义  
   “社区热度”在普通对话里可能是产品功能，在地图页里也可能是排序维度。必须结合 agent 模式和上下文判断，不能只看关键词。

## 2. 已修复策略

### 产品意图放宽

社群、社区圈、心愿单、地图、账号、详情、反馈纠错等产品词，如果没有明确餐饮需求，优先走产品功能回答，不推荐餐厅卡片。

示例：

- “社群相关事项都有哪些” -> 解释社区圈/社群内容，不出卡片。
- “社区里一般能看什么内容” -> 解释热帖、探店、评价、求推荐，不出卡片。
- “这个产品除了推荐餐厅还能干嘛” -> 解释小觅、地图、社区圈、心愿单。

### 泛问题兜底分流

如果用户问题既不是明确产品问题，也不是明确吃喝需求，小觅先问清方向：

> 我先不直接推餐厅，避免又给你兜底错方向。你现在是想了解产品功能，还是想让我帮你选吃的？

### 地图重排例外

地图页里的“不要只看最近，也看看社区热度”不能被当成产品说明。它属于地图排序维度，应继续进入地图推荐/重排逻辑。

## 3. 1 万条评测数据够不够

结论：1 万条可以作为下一阶段目标，但“数量”不是核心，结构才是核心。

推荐拆成三层：

### L1：核心回归集，5000 条

每次改代码必须跑，速度快，覆盖最高风险场景：

- 明确品类：火锅、甜品、奶茶、清淡、快餐
- 忌口：不辣、不吃猪肉、孕妇、生冷、过敏
- 产品问题：社区圈、心愿单、地图、详情、账号
- 边界问题：你是谁、怎么问、价格准吗、推荐依据
- 上下文：继续上一轮、重启口味、换地点、保留某家
- 生成结构：100 个核心 seed × 10 种自然说法 × 5 类场景维度

### L2：扩展评测集，10000 条

用于版本发布前跑，覆盖说法多样性：

- 同一个 intent 的 50-200 种自然说法
- 口语、错别字、省略句、反问句、抱怨句
- 多条件组合：预算 + 交通 + 情绪 + 社交 + 时间
- 产品功能组合：社区 + 心愿单 + 地图 + 详情页
- 地图空间组合：地铁、商场、展会、停车、回家、自习

### L3：真实日志回放集，持续累积

最重要。把真实用户失败问题加入评测，例如：

- “我问社群相关事项，为什么推餐厅”
- “想吃甜的却推东北菜”
- “你是谁却推荐餐厅”
- “水果超出数据库却硬推餐厅”

真实失败样例的价值高于批量合成样例。

## 4. 是否需要微调

当前阶段不建议马上做模型微调。原因：

1. 主要错误来自前置意图路由和数据标注，不是模型表达能力不足。
2. 微调无法保证不出卡片，必须由业务决策层硬控。
3. 数据库候选不准时，微调只会更自信地说错。
4. 目前更需要“意图分类 + 候选过滤 + 匹配反思 + UI动作”的流水线稳定。

推荐顺序：

1. 先修规则门控和评测。
2. 再用 LLM 做意图分类辅助。
3. 最后在真实日志足够后，考虑微调一个轻量 intent classifier，而不是直接微调整个对话模型。

## 5. 要不要改参数

可以调，但不是主要矛盾。

推荐参数：

- 意图分类：低温度，`temperature = 0-0.2`，确保稳定。
- 推荐解释：中低温度，`temperature = 0.3-0.5`，保证表达自然但不乱编。
- 创意文案/社区帖子总结：可稍高，`temperature = 0.6-0.8`。

关键点：

不要让同一个模型调用同时承担“分类、检索、推荐、闲聊、解释”全部任务。分类要稳，表达可以活。

## 6. 如何让 agent 变灵活

灵活不是让模型自由发挥，而是让它有更多正确分流路径。

### 需要的决策路径

1. 产品功能回答  
   社区圈、心愿单、地图、账号、详情页。

2. 餐厅推荐  
   用户明确口味、预算、位置、人数、场景。

3. 多轮追问  
   用户需求模糊，不急着推荐。

4. 地图规划  
   用户提到位置、路线、下一站、地铁、商场、停车。

5. 数据库外兜底  
   水果、生鲜、便利店、药店等，不出餐厅卡片，转地图搜索/生活服务思路。

6. 反馈纠错  
   太贵、太远、不符合、保留某家、换一批。

7. 泛问题引导  
   不知道用户想干嘛时，先问产品功能还是选吃的。

## 7. 下一阶段建议

1. 当前核心评测集已扩到 5000 条，后续再扩到 10000 条作为发布前大集。
2. 增加产品功能类样例到至少 1000 条，覆盖社区、心愿单、地图、详情、账号、反馈、入口失效。
3. 增加真实失败日志表，每次用户发现一次错误，就加入回归集。
4. 把小觅拆成两步：
   - 第一步：意图分类和动作决策。
   - 第二步：根据动作生成回复或推荐。
5. 对推荐做反思校验：
   - 用户问的是什么？
   - 这批卡片是否真的匹配？
   - 是否应该不出卡片？
   - 文本和卡片是否一致？

## 7.1 本轮重构：先识别意图，再决定动作

这轮不再把所有输入都交给“推荐生成”兜底，而是拆成两步：

1. 意图识别层  
   先输出 `IntentFrame`：主意图、动作、置信度、槽位、判断理由。

2. 动作执行层  
   根据意图进入不同工作链：产品问答、追问澄清、餐厅推荐、地图规划、数据库外兜底、闲聊分流。

当前动作矩阵：

| 主意图 | 触发输入 | 动作 | 是否出餐厅卡 |
|---|---|---|---|
| `meta_or_product_help` | 你是谁、怎么用、社群、心愿单、地图、隐私、加载慢 | 回答能力/入口/边界 | 否 |
| `food_recommendation` | 明确吃喝、口味、预算、人数、地点 | 精准筛选餐厅 | 是 |
| `vague_food_need` | 不知道吃什么、随便、你看着办 | 追问关键维度 | 否 |
| `vague_food_need_with_memory` | 上轮有口味，新一轮又模糊 | 确认继续旧口味还是重启 | 否 |
| `map_rerank_or_spatial_planning` | 地图页重排、路线、点位、保留 | 更新地图候选和空间解释 | 是/地图点位 |
| `out_of_scope_category` | 水果、生鲜、便利店、药店 | 非餐厅兜底 | 否 |
| `lifestyle_planning_unclear` | 累、约会、带娃、散步、办公、回家但没说吃 | 先判断是生活安排还是吃饭需求 | 否 |
| `small_talk_or_opening` | 你好、在吗、随便聊 | 说明小觅能做什么并给入口 | 否 |
| `unclear_non_food` | 不能可靠判断 | 分流产品功能/选吃的 | 否 |

这个拆法的目的不是让 agent 更死板，而是防止“看不懂就推荐餐厅”。灵活性放在每条工作链内部：追问、记忆、重筛、地图规划、产品说明各自有不同策略。

## 7.2 真实失败日志回放集

新增 `agent_failure_replay_cases.py`，把真实失败问法变成长期回归测试。当前首批覆盖：

- “你是谁”不能推荐餐厅。
- “社群相关事项都有哪些”必须解释社区圈。
- “我想吃甜的”首推必须是甜品/饮品类，不能是东北菜、海鲜、日料。
- “我想吃凉的”不能推荐热炒、火锅、炒菜。
- “想吃冰一点但能当一餐”首推要偏凉面、冷食、沙拉、轻食。
- “想买水果”属于数据库外，不能硬凑餐厅卡。
- 日常状态/闲聊输入先分流，不直接塞推荐。

之后每次线上或调试发现错答，都按同样格式追加到回放集，要求每次发版必过。

## 8. 用户视角问题地图

后续数据投喂不能只围绕“吃什么”，要覆盖用户把小觅当作产品助手时的自然问题。

### A. 产品入口类

- 社区圈在哪里？
- 心愿单怎么打开？
- 地图模式怎么进？
- 菜单和评价在哪里看？
- 个人页有什么用？

期望：回答入口和操作，不推荐餐厅。

### B. 产品概念类

- 社群相关事项有哪些？
- 社群和社区圈是一回事吗？
- 小觅 agent 和地图小觅区别是什么？
- 这个产品除了推荐餐厅还能干嘛？

期望：解释概念、能力边界和典型用法。

### C. 数据可信类

- 为什么我附近有些店搜不到？
- 价格和营业时间准吗？
- 评分依据是什么？
- 这家店地址错了怎么改？
- 可以新增餐厅吗？

期望：说明数据覆盖、更新时间、用户反馈和纠错入口。

### D. 隐私与权限类

- 不开定位还能用吗？
- 定位会不会保存我的位置？
- 为什么要开定位？
- 可以只搜索地点不授权吗？

期望：说明定位用途、替代方式和隐私边界。

### E. 异常处理类

- 地图空白怎么办？
- 小觅回复很慢怎么办？
- 按钮点了没反应怎么办？
- 心愿单打不开怎么办？

期望：给排查步骤，不把错误兜底成餐厅推荐。

### F. 社区治理类

- 评论不合适怎么举报？
- 评价写错了能改吗？
- 发帖有什么规则？
- 能不能匿名？

期望：说明评价/帖子/举报/审核逻辑。

### G. 能力边界类

- 可以直接外卖下单吗？
- 能帮我付款吗？
- 能帮我订座吗？
- 能打电话给商家吗？

期望：明确当前产品边界，给可行下一步，不假装已完成动作。

### H. 泛问题类

- 我随便问个问题你会做什么？
- 我不知道怎么用。
- 你现在能帮我什么？

期望：先分流：了解产品功能，还是帮你选吃的。

### I. 双义词场景

同一个词在不同上下文可能代表不同意图：

- “社区热度”在产品说明中是社区功能，在地图页可能是排序维度。
- “收藏”可能是心愿单操作，也可能是用户说“我喜欢这家”。
- “定位”可能是权限问题，也可能是地图搜索问题。

期望：结合 agent 模式、上下文和是否有餐饮动作判断，不能只靠关键词。
