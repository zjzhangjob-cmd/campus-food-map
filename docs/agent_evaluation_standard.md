# 小觅 Agent 评测标准 v2

## 目标

小觅的评测不能只看“能不能回答”，而要看三层闭环：

1. 数据标注是否准确：餐厅、菜品、场景标签是否真的匹配用户可能问的关键词。
2. 用户意图是否准确：用户输入要被拆成口味、预算、距离、人数、交通、情绪、社交、身份和下一步安排。
3. 匹配反思是否通过：推荐后要反向检查“候选是否真的符合这句话”，文字、卡片、地图点位必须一致。

评测集规模：

- 当前初始回归集扩展为 5000 条。
- 普通小觅 agent：2500 条，覆盖需求发现、卡片推荐、产品问答、边界兜底、记忆追问。
- 地图小觅 agent：2500 条，覆盖定位、路线、地铁、商场、心愿单、后续安排、时间/交通约束。
- 生成结构：100 个核心 seed × 10 种说法 × 5 类场景维度。
- 5 类场景维度不是简单复述，而是叠加预算、距离/交通、社交场景、后续安排、产品入口/异常处理等约束。

评测的基本流程：

1. 标注校验：检查餐厅主身份、场景标签、菜品标签是否会产生误召回。
2. 意图识别：识别主意图和辅助意图。
3. 候选召回：先做硬过滤，再做排序。
4. 匹配反思：反查候选是否违反用户显式需求。
5. 回复检查：回答是否承认需求、解释原因，并给出下一步操作。

核心产品规则：

- 用户有明确品类指向时，推荐卡片必须精准局限在该品类。  
  例如用户说“火锅”，候选必须来自火锅/小火锅/汤锅/椰子鸡火锅/潮汕牛肉火锅等火锅池，不能混入面馆、奶茶、海鲜、烧肉。
- 数据标注要同时有粗分类和细分类。  
  粗分类用于大方向，例如中餐、饮品、甜品；细分类用于精准召回，例如火锅、奶茶、糖水、咖啡甜点、清汤锅。
- 用户指向不明时，不一定推荐卡片。  
  如果用户说“随便”“不知道吃什么”“你看着办”，应先通过多轮对话问一个关键问题，例如口味、预算、距离、人数、场景或后续安排。
- 用户不满意后，agent 必须带着记忆二次判断。  
  如果上一轮是火锅，用户说“这家不行，换一家”，应继续在火锅池里换，并避开上一轮被否定的店；不能重新随机推荐。
- 用户换了地点但口味变模糊时，必须显式确认上下文。  
  例如上一轮搜火锅，下一轮说“我不知道吃什么，上海南站附近有什么好吃的”，应先问“还想继续火锅，还是这轮重启口味”，不能暗中沿用火锅，也不能直接泛推。
- 用户提问品类超出餐厅库收录范围时，必须走兜底，不出推荐卡片。  
  例如“水果/果切/生鲜/药店/便利店”不是餐厅推荐库的稳定品类，应说明当前库不收录，不硬凑餐厅；可以建议转成地图搜索、商超/便利店思路，或让用户改成餐饮口味继续筛。

典型失败例：

用户说：“我想吃甜的。”

错误：
- 推荐东北菜、川菜、火锅、盖饭等非甜食主导选项。
- 只按评分/距离机械推荐。
- 不追问“甜品/饮品/饭后甜口/蛋糕/奶茶”等关键分支。

合格：
- 识别为 `sweet_craving`。
- 优先推荐甜品、蛋糕、奶茶、咖啡甜点、冰品、糖水、下午茶。
- 如果信息不足，先追问一个关键问题，或给 2-3 个甜口方向。

## 一、意图识别标签

每次用户输入至少识别一个主意图，可识别多个辅助意图。

### 0. 餐饮标签层级

参考大众点评等本地生活产品的常见组织方式，标签拆成四层：

| 层级 | 示例 | 用途 |
|---|---|---|
| 菜系大类 | 西餐、日料、韩餐、泰餐、新疆菜、东北菜、本帮菜、粤菜、海鲜 | 用户明确说大类时做候选池硬过滤 |
| 品类细分 | 意面、披萨、牛排、部队锅、冬阴功、大盘鸡、锅包肉、云吞面、烤串、米线 | 用户说具体品类时映射到对应大类 |
| 场景标签 | 一人食、聚餐、约会、办公、自习、带娃、长辈友好、少排队、近地铁 | 排序和追问，不应单独覆盖菜系 |
| 评价标签 | 口味、环境、服务、性价比、排队、分量、安静、出餐快、可坐、插座 | 解释推荐理由和二次重排 |

当前已纳入硬过滤的大类：

- 西餐：西餐、西式、意面、披萨、牛排、汉堡、brunch、法餐、美式、简餐。
- 日料：日料、日本料理、寿司、刺身、拉面、烧鸟、居酒屋。
- 韩餐：韩餐、韩国料理、韩式烤肉、部队锅、泡菜、石锅拌饭。
- 泰餐：泰餐、泰国菜、冬阴功、咖喱、泰式。
- 新疆菜：新疆、大盘鸡、手抓饭、烤包子、羊肉串。
- 东北菜：东北菜、锅包肉、铁锅炖、地三鲜、饺子。
- 本帮/上海菜：本帮菜、上海菜、本地菜、红烧肉、生煎、小笼。
- 粤菜/茶餐厅：粤菜、港式、茶餐厅、早茶、烧腊、云吞面。
- 烧烤/烤肉：烧烤、烤串、烤肉、羊肉串、夜宵。
- 粉面：面馆、粉、米线、汤面、拌面、酸辣粉、螺蛳粉。
- 咖啡办公：咖啡、办公、自习、插座、安静。
- 茶饮：奶茶、饮品、果茶、茶饮、冷饮。

伪标签规则：

- “下午茶”不能单独召回海鲜、日料、咖啡办公。
- “刺身”默认归日料，不作为普通海鲜需求的召回词。
- “brunch”默认归西餐，不作为咖啡办公的唯一召回词。
- 用户明确菜系时，味型词如“辣/清淡/都行”只能作为修饰，不能覆盖主菜系。

意图防空规则：

- `FOOD_REQUEST_PATTERN` 只能判断“是不是餐饮方向”，不能代替品类识别。
- 所有常见菜系/品类/饮品词必须先经过统一词典归一化，写入 `cuisine` 或 `fine_category`。
- 如果用户输入里出现餐饮实体词，例如“拿铁”“冬阴功”“锅包肉”“云吞面”，即使没有“吃/喝/推荐”动词，也必须进入明确品类意图。
- 推荐链不允许带着空 `cuisine` 和空 `fine_category` 去做泛推荐，除非用户确实只说“随便/不知道吃什么”。
- 评测必须包含 slot 回归：常见提示词输入后，检查 `cuisine` 是否为空或错类。

### 5. 产品功能意图

这类问题的主目标是解释产品、入口和操作闭环。除非用户同时明确提出餐厅需求，否则不出餐厅卡片。

| 标签 | 触发表达 | 正确回答 |
|---|---|---|

| `product_community_post_help` | 怎么发帖、怎么写探店、帖子在哪里发 | 说明发帖入口和建议内容：体验、排队、适合人群、避雷点 |
| `product_wishlist_help` | 心愿单和收藏是不是一个、怎么加入/移出 | 说明心愿单是统一收藏入口，状态会同步 |
| `product_wishlist_map_help` | 心愿单怎么批量放地图、一键规划怎么用 | 说明勾选、批量加入地图、一键规划和路线比较 |
| `product_map_help` | 全屏地图能做什么、地图点位怎么看、没开定位怎么办 | 说明定位/搜索地点、点位、路线、地铁/商场/展会/停车标注 |
| `product_agent_mode_help` | 普通小觅和地图小觅区别、两种 agent 怎么用 | 说明普通 agent 负责需求挖掘，地图 agent 负责空间规划 |
| `product_detail_help` | 菜单/评价/详情/营业时间在哪里看 | 说明可从餐厅卡、帖子餐厅、推荐卡、地图点位进入详情 |
| `product_account_help` | 不登录能不能用、登录后有什么区别 | 说明未登录可浏览/对话，登录后同步心愿单、评价、社区互动 |
| `product_feedback_help` | 推荐不准怎么告诉你、怎么纠错、怎么重筛 | 说明可反馈太贵/太远/不吃某类/保留某家，并按反馈重筛 |
| `product_data_help` | 为什么搜不到、数据准吗、地址错了、想新增餐厅 | 说明数据覆盖、更新时间、纠错和补充信息流程 |
| `product_privacy_help` | 定位会不会保存、不开定位能用吗、隐私安全吗 | 说明定位用途、手动搜索替代和隐私边界 |
| `product_error_help` | 地图空白、加载慢、按钮没反应、小觅回复慢 | 给排查步骤，不把异常兜底成餐厅推荐 |
| `product_review_help` | 评价能改吗、评论怎么举报、发帖规则 | 说明评价、评论、举报和审核逻辑 |
| `product_boundary_help` | 能下单吗、能付款吗、能订座吗、能打电话吗 | 明确能力边界，给可行下一步，不假装完成 |

产品功能意图的 P0 失败：

1. 用户问功能入口或使用方法，却直接推荐餐厅。
2. 用户问社区圈/心愿单/账号等产品问题，回答里没有具体入口或操作。
3. 用户问普通小觅和地图小觅区别，回答没有区分“需求挖掘”和“空间规划”。
4. 用户问推荐不准怎么反馈，回答没有说明可被记住的纠错维度。
5. 用户问隐私、加载失败、数据纠错、支付订座等边界问题时，仍然用餐厅卡片兜底。
6. 用户只是泛泛问“你能做什么/我随便问个问题”，没有先分流产品功能与餐饮推荐。

## 二、意图识别准确性标准

### 动作标准

意图识别不只看标签，还必须判断下一步动作：

| 动作 | 使用场景 | 失败标准 |
|---|---|---|
| `answer` | 你是谁、怎么用、社群、心愿单、隐私、数据、加载慢 | 出现餐厅推荐卡，或没有回答入口/边界 |
| `clarify` | 不知道吃什么、生活状态模糊、上轮记忆冲突、用户只说累/无聊/约会 | 未追问关键维度，直接塞兜底餐厅 |
| `recommend` | 用户明确口味、预算、人数、地点、品类 | 推荐品类与用户需求不一致 |
| `fallback` | 水果、生鲜、药店、便利店等非餐厅库需求 | 硬凑餐厅卡，或假装数据库覆盖 |
| `map_plan` | 地图页、路线、地铁、商场、展会、回家、停车 | 不更新地图语义，或只给普通餐厅卡 |

每条评测都应同时写：

1. 用户原话。
2. 期望主意图。
3. 期望动作。
4. 必须出现/禁止出现的候选标签。
5. 是否允许出推荐卡片。
6. 需要追问的关键问题。

### P0 硬性错误

出现以下情况直接判失败：

1. 用户明确口味，被推荐完全不匹配品类。  
   例如“想吃甜的”推荐东北菜。

2. 用户明确忌口，仍推荐被禁止内容。  
   例如“不吃辣”推荐重庆小面/川菜/火锅。

3. 用户要求替换，地图或卡片仍保留旧推荐且未说明。

4. 地图 Agent 只给文字推荐，没有地图动作或空间理由。

5. 文字推荐和结构化卡片不是同一批餐厅。

6. 用户问边界/元问题时仍强行推荐餐厅。

7. 数据标签误召回。  
   例如海鲜店只因带了“下午茶”场景标签，就被当成甜品候选。

### P1 重要问题

1. 识别了大方向，但没有追问关键分支。  
   例如“甜的”只推甜品，没有问“饭后甜点还是直接吃甜口下午茶”。

2. 推荐理由泛泛，不能解释为什么适合。

3. 推荐数量过多，用户反而更难选。

4. 没有提供下一步操作：加入心愿单、加入地图、查看详情、继续筛选。

### P2 体验问题

1. 语气太机械。
2. 没有复用历史偏好。
3. 没有承认用户反馈。
4. 地图回答缺少“路线/方位/下一站”的语言。

## 三、每类意图的期望回答模板

### 1. 用户只说“我想吃甜的”

合格回答：

> 想吃甜的我先不推正餐啦。你现在更像是想要「饭后甜点/下午茶/奶茶饮品/蛋糕冰品」哪一种？  
> 如果你想直接选，我可以先按附近和少踩雷给你筛 2-3 家甜品/奶茶/咖啡甜点，并放进卡片里。

如果已有位置：

> 我先按你当前位置找甜口选择：甜品、奶茶、咖啡甜点优先，不会给你推正餐。要不要我再按“离你近 / 能坐一会儿 / 适合带走”筛？

期望动作：
- `intent`: `sweet_craving`
- `candidate_filter`: dessert, milk_tea, cafe_dessert, bakery, ice_cream, tangshui
- `must_avoid`: northeastern_food, spicy_food, hotpot, barbecue, rice_bowl
- `next_question`: sweet subtype or dine-in/takeaway

### 2. 用户说“想吃甜的，附近，能坐一会儿”

合格回答：

> 明白，是“甜口 + 附近 + 能坐”的需求，不是正餐。  
> 我会优先找咖啡甜点、蛋糕店、糖水/奶茶里有座位的店，避开只适合外带的小窗口。  
> 这几家可以先看：...

期望动作：
- 普通 Agent：渲染甜品/咖啡甜点卡片。
- 地图 Agent：标甜品点位，区分可坐/外带，显示距离。

### 3. 用户说“不吃辣，预算30以内”

合格回答：

> 收到，不辣和预算 30 是硬条件。我会避开川湘、火锅、重庆小面这类重辣选项，优先看清淡、轻食、粥面、粤式简餐。  

失败：
- 推荐重庆小面、火锅、麻辣烫。

### 4. 用户说“吃完我要去地铁”

合格回答：

> 这是地图规划问题。我会把餐厅和附近地铁站一起标出来，不只看直线距离，还会看吃完去地铁是否顺路。你要坐哪条线或往哪个方向？

期望动作：
- `map_actions`: mark_subway_stations, rank_by_route_to_subway, draw_route_arcs

## 四、推荐候选召回标准

推荐前必须先做候选过滤。

### 甜口过滤

包含任一关键词时进入甜口候选池：

- 用户词：甜的、甜品、蛋糕、奶茶、糖水、冰、冰淇淋、布丁、下午茶、咖啡甜点、烘焙
- 餐厅标签：甜品、奶茶、饮品、咖啡、蛋糕、烘焙、糖水、冰品、甜点

注意：“下午茶”单独出现只能算场景标签，不能直接判定餐厅是甜口候选。甜口候选必须有甜品/饮品主身份，例如菜系或标签包含甜品、奶茶、饮品、蛋糕、糖水、冰品、烘焙、甜点、咖啡甜点。

甜口意图下，以下候选不得作为首推：

- 东北菜、本帮菜、川菜、湘菜、火锅、烧烤、冒菜、盖饭、烤肉、面馆、海鲜、日料、烧肉、刺身、寿司、小龙虾

如果餐厅只是海鲜/日料/烧肉，但被打上“下午茶”场景标签，仍应排除。

除非用户说：

- “正餐后想吃一点甜的”
- “想吃甜口菜”
- “东北菜里有没有甜口菜”

### 忌口过滤

用户说“不吃/别推/讨厌/过敏”时，必须进入硬过滤。

例：

- 不吃辣：过滤辣、麻辣、川菜、湘菜、重庆、火锅、冒菜、串串。
- 海鲜过敏：过滤海鲜、寿司、刺身、虾、蟹。
- 不吃肉：过滤肉类主打店。

### 预算过滤

预算表达：

- “30以内”“人均30”“不超过30”：`price_max <= 30` 优先。
- 如果没有完全匹配，可放宽，但必须说明“完全符合的不多，我放宽到 xx”。

## 五、对话策略标准

### 信息不足时

只问一个最关键问题，不连环问。

好：

> 你这个“甜的”更偏奶茶甜品，还是想找能坐的下午茶？

模糊需求：

> 我先不硬塞餐厅卡片，咱们把范围缩小一点。你现在更想要快速吃饱、清淡舒服、想吃点甜的、多人聚餐，还是找个能坐一会儿的地方？

不好：

> 你在哪？预算多少？几个人？想奶茶还是蛋糕？要不要坐？什么时候吃？

### 信息足够时

直接给 2-3 个选择，并解释为什么。

### 用户反馈否定时

必须先承认，再调整。

好：

> 对，这家确实偏贵，我把预算权重拉高，换成 30-40 内更稳的。

不好：

> 你可以再看看这家。

```json
  "failure_if": [

```

自动评测至少检查：

1. 意图标签是否命中。
2. 推荐候选是否包含期望标签。
3. 推荐候选是否包含禁止标签。
4. 回答是否包含追问或下一步操作。
5. 普通 Agent 是否卡片化承接。
6. 地图 Agent 是否有地图动作。
7. 边界问题是否不渲染餐厅卡片。
8. 匹配反思是否发现“伪标签”或“文本卡片不一致”。
9. 明确品类是否严格限制候选池。
10. 模糊需求是否允许无卡片追问。
11. 负反馈后二次推荐是否避开上一轮并保留有效偏好。
12. 新地点 + 模糊需求是否触发“延续上一轮还是重启对话”的确认。
13. 未收录品类是否不生成餐厅卡片，并提供兜底路径。

5000 条评测集覆盖：

- 口味：甜、辣、清淡、热汤、素食、低糖、不吃猪肉、不吃海鲜。
- 预算：15、30、40、80、100+，以及“便宜但别太差”。
- 距离：附近、10分钟内、不想走远、顺路、不要反方向。
- 交通：地铁、打车、开车停车、回家方向、赶火车、换乘站。
- 情绪：累、焦虑、纠结、庆祝、想被安慰、社交压力。
- 社交：一人食、约会、家庭、带娃、带老人、同事聚餐、AA。
- 身份：上班族、游客、家长、老人同行、孕妇同行、轮椅同行。
- 环境：安静、热闹、能办公、能坐久、商场、少露天、安全路线。
- 边界：你是谁、怎么问、能做什么、推荐依据、人均解释、没定位怎么办。
